--rollback segments
	--portion of database storage that records the "before" image of data before a transaction modifies it.
	--store undo information to enable transactions to be rolled back, maintain read consistency for other users, and assist in database recovery after failures.
	--In modern Oracle databases, the AUTO undo management feature handles this functionality automatically, making the manual management of rollback segments obsolete for databases not in manual mode. 
	--key functions
		--Transaction Rollback - If a transaction needs to be reversed (either intentionally or due to an error), the undo information in the rollback segment is used to return the data to its state before the transaction began. 
		--Read Consistency - By storing the original data, rollback segments ensure that a user performing a query sees the data as it was at the start of their transaction, even if other transactions are modifying the data concurrently. 
		--Database Recovery - During a database failure, the rollback segments are used to undo any uncommitted changes, allowing the database to be recovered to a consistent state. 	
	--Automatic vs. Manual Mode 
		--Manual Mode - In older Oracle configurations, database administrators manually created and managed rollback segments, using statements like CREATE ROLLBACK SEGMENT.
		--Automatic Mode - Modern Oracle databases default to AUTO undo management, where the system automatically creates and manages undo segments (the modern term for rollback segments) to handle undo information.	
	--individual Oracle tables do not have their own rollback segments; rather, rollback segments (or undo segments under automatic undo management) are allocated to an Oracle instance and are shared by all transactions within that instance.	
	--states for an Oracle rollback segment are ONLINE, OFFLINE, NEEDS RECOVERY, PARTLY AVAILABLE, and UNDEFINED. 
		--ONLINE - The segment is available and contains data from active transactions, ready for use by the database instance. 
		--OFFLINE - The segment is not currently acquired by any instance and can be brought online when needed. 
		--NEEDS RECOVERY - The segment holds data from an uncommitted transaction that cannot be rolled back because the relevant data files are inaccessible or corrupted. 
		--PARTLY AVAILABLE - segments involved in an in-doubt distributed transaction that is unresolved due to failures, like network issues, preventing the transaction from completing or rolling back. 
		--UNDEFINED - rollback segment does not exist or has not been initialized within the database, as per the DBA_ROLLBACK_SEGS view. 
	--How to Check a Rollback Segment's State => SELECT segment_name, status FROM dba_rollback_segs;	
	--The two main types of rollback segments are Private Rollback Segments and Public Rollback Segments. 
		--Private segments are explicitly acquired by a specific database instance, 
		--public segments are available in a pool for any instance to use. 
		--SYSTEM rollback segment is a special, non-droppable segment created by default during database creation, which an instance always acquires and uses for system transactions. 
--difference between sys and system user in oracle

--components of an Oracle database architecture 
	--3 parts
		--Instance: Background processes + memory (SGA, PGA)
		--Database: Physical files (data/control/redologs)
		--Listener: Accepts user connection requests
	--Oracle Instance (The Logical Layer) - The instance is the set of memory structures and background processes that manage the database files. 
	--Memory Structures:
		--System Global Area (SGA): A shared memory region allocated when the instance starts. It includes the 
			--Database Buffer Cache (holding data blocks read from disk), 
			--Shared Pool (storing parsed SQL and data dictionary data), 
			--Redo Log Buffer (tracking changes to the database).
		--Program Global Area (PGA): Private memory allocated for each server and background process. It stores session data, such as sort areas and bind variable values. 
	--Background Processes:
		--DBWn (Database Writer): Writes modified (dirty) data blocks from the buffer cache to the data files on disk.
		--LGWR (Log Writer): Writes redo log entries from the redo log buffer to the online redo log files.
		--SMON (System Monitor): Performs instance recovery at startup and cleans up temporary segments.
		--PMON (Process Monitor): Cleans up failed user processes and releases their resources.
		--CKPT (Checkpoint): Signals the DBWn to write dirty buffers to disk and updates data file headers and control files with checkpoint info. 
	--Oracle Database (The Physical Layer) This refers to the actual files stored on the server's disk. 
		--Data Files: Contain the actual user data, such as tables and indexes. 
	--Control Files: Metadata files that store the database's physical structure, including the database name and the location of other files. 
	--Online Redo Log Files: Store changes made to the database to ensure data can be recovered in the event of a system failure. 
	--Additional Files: Includes the Parameter File (defines instance configuration), Password File (authenticates privileged users), and Archive Log Files (copies of redo logs used for point-in-time recovery). 
	--Logical Storage Structures - These structures provide an abstraction over the physical data files for finer management. 
		--Tablespaces: The primary logical container; each tablespace is made up of one or more physical data files.
		--Segments: A set of extents allocated for a specific database object, like a table or index.
		--Extents: A specific number of logically contiguous data blocks.
		--Data Blocks: The smallest unit of storage in an Oracle database, corresponding to a specific number of bytes on disk. 
	--Networking and User Processes
		--User Process: The application or tool that initiates a request to the database.
		--Server Process: Created by the instance to handle requests from the user process, such as parsing and executing SQL.
		--Oracle Net Listener: A separate process that listens for incoming client connection requests and hands them off to a server process. 
--tablespaces - logical storage units that map to physical datafiles on disk. They are categorized based on their purpose and how they manage space.
	--PERMANENT TABLESPACE => contains persistent schema objects that are stored in data files
	--TEMPORARY TABLESPACE => contains schema objects that are stored in temp files that exist during a session.
		--used for temporary operations that require disk space, such as sorting, hashing, and large object processing, especially when the operation cannot be completed entirely in memory.
	--UNDO TABLESPACE => manage undo data if the Oracle database is being run in automatic undo management mode.
		--Undo data essentially contains "before" images of data blocks modified by transactions.
	--5 default tablespaces =>SYSTEM, SYSAUX, USERS, UNDOTB3S1, TEMP (know these)
		--all 5 tablespace are automatically generated when any database is created in the Oracle database system
		--system tablespace -contains the data dictionary tables for the entire database and always remains online.
			--essential, mandatory administrative hub of an Oracle database, created automatically at database creation
			--stores the data dictionary, internal PL/SQL program units (stored procedures/functions/packages), and system-level metadata. 
			--always online when the database is open and contains the SYS schema, serving as the core repository for database management information
		--sysaux - mandatory, auxiliary tablespace introduced in 10g to store non-core database metadata, reducing load and fragmentation on the SYSTEM tablespace
			--acts as a central repository for components like the Automatic Workload Repository (AWR), Enterprise Manager, and LogMiner, improving performance and manageability. 
		--users tablespace - default permanent, locally managed tablespace used to store application data, user tables, and indexes	
			--keeps application data separate from system data (contained in SYSTEM/SYSAUX), enhancing performance, security, and administrative control, such as setting quotas and backing up data
		--undo tablespace - to store "before-images" of data modified by transactions. 
			--essential for transaction rollbacks, read consistency, and flashback operations
		--temp tablespace - used to store data for operations that exceed available memory (PGA), such as large sorts, hash joins, and Global Temporary Tables.
			--How to Check TEMP Usage
				--Space is allocated the first time it is used and then managed internally; as a result, it may appear "full" in standard reports even when the internal space is available for reuse.
				--run this query => SELECT * FROM dba_temp_free_space;
				--Common Operations Requiring TEMP tablespace usage
					--Sorting: ORDER BY, DISTINCT, GROUP BY, and UNION.
					--Joins: Hash joins and sort-merge joins.
					--DDL Operations: Index rebuilds or creating large tables.

--dbms_scheduler package
	--below taken from https://db-master.com/oracle/summary-of-dbms_scheduler-in-oracle/
	--Schedule jobs to run PL/SQL blocks, procedures, or external executables at scheduled intervals
	--repeat_interval parameter specifies how frequently a job should run
	--DBMS_SCHEDULER.create_schedule creates a standard interval =can be applied to multiple jobs
		--so you create the standard schedule first and then apply it to job during DBMS_SCHEDULER.create_job
	--run procedure example is below
	BEGIN
	  DBMS_SCHEDULER.create_job (
		job_name        => 'MY_SCHEDULED_JOB',
		job_type        => 'PLSQL_BLOCK',
		job_action      => 'BEGIN my_procedure; END;',
		start_date      => SYSTIMESTAMP,
		repeat_interval => 'FREQ=DAILY; BYHOUR=10; BYMINUTE=0; BYSECOND=0',
		enabled         => TRUE
	  );
	END;
	/	
	--an enable/disable/drop jobs=>see below
	BEGIN
	  DBMS_SCHEDULER.enable('MY_SCHEDULED_JOB');
	  DBMS_SCHEDULER.disable('MY_SCHEDULED_JOB');
	  DBMS_SCHEDULER.drop_job('MY_SCHEDULED_JOB');
	END;	
	--to run job immmediately
	BEGIN
	  DBMS_SCHEDULER.run_job('MY_SCHEDULED_JOB');
	END;	
	--see existing jobs info in dba view dba_scheduler_job_run_details
	--job chains
		-- define and manage a sequence of related jobs, specifying their execution order and dependencies
		--useful for workflows where the completion of one task triggers the next.
		--condition parameter in the DBMS_SCHEDULER.define_chain_rule procedure specifies the criteria under which a chain rule will be applied
			--condition can reference the state of steps within the chain, such as whether a step has succeeded, failed, or completed
			--examples are below
				# Always True: This condition always evaluates to true, meaning the rule will always be applied.
				'TRUE'
				# Step Completed Successfully: This condition checks if a specific step has completed successfully.
				'STEP_1 COMPLETED'
				# Step Succeeded: This condition checks if a specific step has succeeded.
				'STEP_1 SUCCEEDED'
				# Step Failed: This condition checks if a specific step has failed.
				'STEP_1 FAILED'
				# Step Skipped: This condition checks if a specific step was skipped.
				'STEP_1 SKIPPED'
				# Multiple Steps Completed: This condition checks if multiple steps have completed.
				'STEP_1 COMPLETED AND STEP_2 COMPLETED'
				# One of Multiple Steps Succeeded: This condition checks if any one of multiple steps has succeeded.
				'STEP_1 SUCCEEDED OR STEP_2 SUCCEEDED'
				# Step Finished (either succeeded or failed): This condition checks if a specific step has finished, regardless of the outcome.
				'STEP_1 FINISHED'
				# Chained Conditions: This condition chains multiple conditions together with logical operators.
				'(STEP_1 SUCCEEDED OR STEP_2 FAILED) AND STEP_3 COMPLETED'			
		--DBMS_SCHEDULER.create_event_schedule
			--used when a schedule is based on an event rather than date/time
			--useful for jobs that need to run in response to database events or external events, 
				--such as file arrivals, message queue notifications, or custom application events.
--dynamic performance views (interview question)
	--these are the V$_ views
	--special, read-only virtual tables that provide real-time information about an Oracle database's internal memory structures, performance, and current activity. 
	--Commonly Used Views
		--V$SESSION - view is essential for DBAs to diagnose performance issues, identify locking contention, and monitor resource consumption.
			--real-time information on all active and inactive user/background sessions. 
			--who is connected, the status of their session (active/inactive), what SQL they are executing, what resources they are consuming, and what wait events are causing bottlenecks.
			--Key information available in V$SESSION includes:
				--Session Identification: Unique identifier (SID), serial number (SERIAL#), auditing session ID (AUDSID), and session address (SADDR).
				--User/Machine Info: Oracle user (USERNAME), operating system user (OSUSER), and the client machine (MACHINE) or terminal connected.
				--Session State: Whether the session is currently active or waiting (STATUS), along with the last statement executed (COMMAND).
				--Wait Events: What the session is currently waiting for (EVENT), how long it has been waiting (SECONDS_IN_WAIT), and who is blocking it (BLOCKING_SESSION).
				--SQL Information: The SQL_ID and SQL_HASH_VALUE of the SQL statement currently being executed or the last executed query.
				--Process Information: Address of the OS process owning the session (PADDR), allowing a join with V$PROCESS to kill session
		--V$SQL - provides detailed statistics and information about shared SQL areas (cursors) currently in the library cache
			--V$SQL shows one row for each child cursor of a SQL statement, allowing you to see specific details if the same query has multiple execution plans.
			--Key Information Provided
				--SQL Text: The first 1,000 characters of the statement (SQL_TEXT) or the full text via a CLOB (SQL_FULLTEXT).
				--Execution Metrics: Total number of executions (EXECUTIONS), fetches (FETCHES), and rows processed (ROWS_PROCESSED).
				--Resource Usage: Cumulative CPU time (CPU_TIME) and database elapsed time (ELAPSED_TIME) in microseconds.
				--I/O STATISTICS (KNOW THIS): DISK READS (DISK_READS) AND LOGICAL READS (BUFFER_GETS), WHICH ARE CRITICAL FOR IDENTIFYING RESOURCE-INTENSIVE QUERIES.
					--Logical Reads (BUFFER_GETS): Number of times a block is read from memory (Buffer Cache). => Fast, as data is already in memory.
					--Physical Reads (DISK_READS): Number of times a block is read from physical disk storage. =>Slow, as data must be fetched from the disk, which is slower than memory.
						--To reduce this, optimize indexing to ensure data is in the cache
					--Ideally, you want to maximize the buffer cache hit ratio, meaning most reads should be logical rather than physical.	
				--Optimizer Data: The cost assigned by the optimizer (OPTIMIZER_COST) and the specific execution plan identifier (PLAN_HASH_VALUE).
				--Application Info: The module (MODULE) or action (ACTION) name set by the application to help map queries back to specific business functions
		--V$PROCESS - dynamic performance view that provides real-time information about active Oracle background and user processes
			--view is crucial for database administrators (DBAs) to map a high CPU-consuming operating system process back to a specific Oracle user or session
			--Key Information Provided by V$PROCESS:
				--Process Identification: Contains the Oracle PID, the operating system process identifier (SPID) for Unix/Windows, and the thread ID (STID).
				--Process Activity: Shows what a specific process is currently doing, including active wait events, such as which latch a process is waiting for (LATCHWAIT) or spinning on (LATCHSPIN).
				--Connection Details: Displays the user terminal, machine name, and program name for each process.
				--Process State: Provides the memory address of the process state object (ADDR), useful for low-level diagnostic linking to other V$ views like V$SESSION.
		--V$INSTANCE - provides real-time information about the current database instance's state, including its name, status (e.g., STARTED, MOUNTED, OPEN), host machine name, version, and startup time
			--This view is useful for quick checks on instance availability and monitoring the status of the database after startup or during maintenance.
			--Key Details Provided by V$INSTANCE:
				--Instance State (STATUS): Indicates if the instance is STARTED, MOUNTED, or OPEN.
				--Identity (INSTANCE_NAME, HOST_NAME): Identifies the specific instance name and the server it is running on.
				--Version Information (VERSION): Displays the Oracle Database version.
				--Startup Time (STARTUP_TIME): Tells you when the instance was last started.
				--Parallel Mode (PARALLEL): Indicates if the instance is running in Oracle Real Application Clusters (RAC) mode (YES or NO).
				--Archiver Status (ARCHIVER): Shows the state of the archiver process (STARTED, STOPPED, or FAILED).
				--Logins (LOGINS): Indicates if logins are ALLOWED or RESTRICTED
		--Some Essential V$ Views Every Oracle Pro Should Know:
			--V$PARAMETER: All about your initialization parameters.
			--V$DATABASE: Database status, ID, creation date, and more.
			--V$LOCK: Crucial for identifying and resolving database locks.
			--V$TRANSACTION: Information on current active transactions.
			--V$LOGFILE, V$LOG, V$ARCHIVED_LOG: Your go-to for redo and archive log details.

			--session activity
			--i/o stats
			--memory usage

-- Oracle instance=>collection of memory structures and background processes that manage an Oracle database.		
	--System Global Area (SGA)- shared memory area accessible by all background processes and server processes. It includes:
		--shared among all processes within a database instance
		--Shared pool- contains the 
			--Library Cache (stores parsed SQL statements and PL/SQL code) 
			--Data Dictionary Cache (stores metadata about database objects)
		--Redo Log Buffer - Stores changes made to the database before they are written to redo log files, ensuring recoverability.	
			--acts as an in-memory staging area for redo information before it is written to the online redo log files on disk.
			--Redo Entries contain the necessary information to reconstruct database changes, ensuring recoverability in case of instance or system failures.	
			--Log Writer (LGWR) Process -responsible for writing the contents of the redo log buffer to the online redo log files.
		--Database Buffer Cache - Stores copies of data blocks read from data files, reducing disk I/O.	
	--Program Global Area (PGA): A private memory area allocated to each server process or background process. 
		--PGA is private to each process - accessible only by the process to which it belongs.
		--It contains data and control information for that specific process, such as sort areas and session information.	
			--SQL Work Areas: These are memory-intensive areas used by operators like sorts (for ORDER BY, GROUP BY, etc.), hash joins, bitmap merges, and bitmap creations. 
			--Private SQL Area - stores information related to SQL statement execution, including bind variable values (persistent area) and execution state information (run-time area).
		--Memory within the PGA is allocated and deallocated as needed by the server or background process to perform its tasks.
		--Automatic PGA Memory Management - you can set a target size for the total instance PGA. The database then dynamically tunes the sizes of individual PGAs within this target, optimizing memory utilization for various operations. 
			--This is generally the recommended approach for PGA management. 
			--Manual PGA management, while still supported, involves setting maximum work area sizes for each type of SQL operator and is less commonly used.
	--Background Processes
		--DBWn (Database Writer): Writes modified data blocks from the database buffer cache to data files.
		--LGWR (Log Writer): Writes redo entries from the redo log buffer to redo log files.
			--redo logs => 2 or more preallocated files that store all changes made to the database as they occur (know this), used in instance recovery
		--PMON (Process Monitor): Cleans up failed user processes and releases resources.
		--SMON (System Monitor): Performs instance recovery, cleans up temporary segments, and coalesces free extents.
		--CKPT (Checkpoint): Updates control files and data file headers during checkpoints.
			--synchronizes the in-memory data in the database buffer cache with the data files on disk
			--It ensures data consistency and enables faster database recovery after an instance failure. 
		--ARCH (Archiver): Archives filled redo log files when in ARCHIVELOG mode.	
			--primary function is to copy online redo log files to an archive destination after a log switch occurs.
			--ARCn processes are only active when the Oracle database is configured in ARCHIVELOG mode and automatic archiving is enabled
			--ARCHIVELOG mode is a database operating mode that saves filled online redo log files to a designated location, enabling complete, point-in-time recovery and hot backups.
				--essential for production databases to prevent data loss from media failures (e.g., disk crashes)
				--Key Features & Advantages:
					--Complete Recovery: Protects against data loss by allowing recovery from disk failures.
					--Hot Backups: Enables backups while the database is open and active.
					--Standby Databases: Essential for supporting Data Guard/standby configurations.
					--Automatic Archiving: Uses the ARCH process to move logs, typically configured automatically.
-shared pool - component of the system global area (SGA) within the database instance.
	--responsible for caching various types of program data
		--stores parsed SQL, PL/SQL code, system parameters, and data dictionary information
	--shared pool consists of the following subcomponents:
		-- library cache is a shared pool memory structure that stores executable SQL and PL/SQL code.
		-- reserved pool is a memory area in the shared pool that Oracle Database can use to allocate large contiguous chunks of memory
		--data dictionary cache stores information about database objects (that is, dictionary data)
			--serves as a central repository of metadata, which is data about the database itself
			--read-only set of tables that provides information about the database. 
			--All the data dictionary tables and views for a given database are stored in that database's SYSTEM tablespace.
			--primary uses 
				--provides info about schema objects
					--contains comprehensive information about the database's structure, including definitions of all schema objects (tables, views, indexes, procedures, functions, triggers, etc.), their properties (column names, data types, default values, integrity constraints), and the relationships between them.
				--user and security info - stores details about Oracle Database users, the privileges and roles granted to them, and auditing information related to user activities and object access.
				--tracking space allocation and usage - amount of space allocated for and currently used by various schema objects, aiding in space management and capacity planning.
				--facilitating database administration and monitoring - Database administrators utilize the data dictionary views to monitor database performance, identify potential issues, and manage database resources effectively.
				--supporting application development - Developers can query the data dictionary to understand the database schema, retrieve object definitions, and ensure data consistency and integrity within their applications.
		--server result cache is a memory pool within the shared pool that contains the SQL query result cache and PL/SQL function result cache
			--Good candidates for result caching are frequently invoked functions that depend on relatively static data.
		--Other components include enqueues, latches, information lifecycle management (ILM) bitmap tables, active session history (ASH) buffers, and other minor memory structures.

--Oracle RAC (Real Application Clusters) -a database architecture that allows multiple instances of a database to run on different servers, while still appearing as a single database to the application	
	-- introduced in 2001 with Oracle9i. 
	--It's a good option for customers with mission-critical databases, where the failure of applications running on those databases would have a significant negative impact on the business
	--How it works
		--Multiple instances: In a RAC setup, multiple Oracle database instances are running on different servers (called nodes).	
		--Shared storage: All of these instances share the same database files located on a shared storage device.
		--Oracle Clusterware: This is the foundation of the cluster, a mandatory component that manages the cluster's health and resources.
		--Communication: The nodes communicate with each other over a private network and coordinate access to the shared storage.
		--Load balancing: When a user connects, a listener directs the request to the least busy node, which helps in load balancing and improves performance.
		--Failover: If a node fails, Oracle Clusterware detects the failure and automatically reroutes the user's connection to one of the remaining healthy nodes in the cluster. 
	--High availability - RAC protects against hardware and software failures by automatically failing over application connections to surviving servers in the cluster.

		--GENERATED ALWAYS: Oracle always generates a value for the identity column. You’ll encounter an error if you attempt to insert a value into the identity column.
			--part of create table command
			--used to define a generated column (also known as a computed column or virtual column) whose value is automatically derived from an expression based on other columns in the same table
				--This means the value of such a column is always calculated and cannot be directly inserted or updated by users.
			--syntax =>col_name data_type GENERATED ALWAYS AS (expression) [VIRTUAL | STORED]	
				--VIRTUAL (default): The column's value is computed on the fly when accessed. It does not occupy storage space.
				--STORED: The column's value is computed and stored in the table. 
					--can improve query performance if the column is frequently accessed, but it consumes storage space.
			--Read-only - cannot explicitly insert or update values into a GENERATED ALWAYS AS column. Any attempt to do so will result in an error.
			--Deterministic expressions - expression used for generation must be deterministic, meaning it consistently returns the same result for the same input values. It cannot contain non-deterministic functions (like SYSDATE or DBMS_RANDOM).
			--No cyclic dependencies - Generated columns cannot reference other generated columns if it creates a cyclic dependency.
			--Constraints - Generated columns can have constraints like NOT NULL, UNIQUE, and can be part of a PRIMARY KEY. 
		--GENERATED BY DEFAULT: Oracle generates a value for the identity column if you don’t provide any value. If you provide a value, Oracle will insert that value into the identity column. 
			--For this option, Oracle will issue an error if you insert NULL into the identity column.
		--GENERATED BY DEFAULT ON NULL: Oracle generates a value for the identity column if you provide NULL or no value.
			--identity options
				--START WITH initial_value controls the initial value to use for the identity column. 
					--The default initial value is 1.
				--INCREMENT BY internval_value defines the interval between generated values. By default, the interval value is 1.
				--CACHE defines a number of values that Oracle should generate beforehand to improve the performance. 
					--use this option for the column that has a high number of inserts.
		--identity column restrictions
			--Each table has a maximum of one identity column.
			--The data type of the identity column must be a numeric data type. You cannot use a user-defined data type with the identity clause.
			--When you create a new table with the CREATE TABLE AS SELECT statement, Oracle does not transfer the identity column to the new table.
			--You cannot define an identity column with a DEFAULT constraint.
			--The encryption algorithm for encrypted identity columns can be inferred; therefore, you should use a strong encryption algorithm.
			--The inline constraint of the identity column must not conflict with the NOT NULL and NOT DEFERRABLE constraint stated by the identity clause.

--compound trigger -  combines multiple timing points within a single trigger body.

		--After Inserting Table Data - It is generally more efficient to create indexes after inserting or loading data into a table (e.g., using SQL*Loader or Import). 
			--Creating indexes before data loading means Oracle must update each index with every row insertion, slowing down the load process. 
			--The exception is for clusters, where an index must be created before data insertion.
		--For Frequently Queried Columns -Create indexes on columns frequently used in WHERE clauses, ORDER BY clauses, GROUP BY clauses, or join conditions. 
			--This significantly improves query performance by allowing Oracle to quickly locate relevant data without full table scans.
		--On Large Tables -
			--Indexes provide the most benefit on large tables where a full table scan would be very costly. 
			--For small tables (e.g., fewer than 100 rows), the overhead of maintaining an index might outweigh the performance gains.
		--For Primary and Unique Keys - Oracle automatically creates indexes for primary and unique key constraints.
		--For Foreign Keys (Optional but Recommended) - Consider creating indexes on foreign key columns, especially if they are frequently used in joins or lookups.
		--Function-Based Indexes - If queries frequently use a function on a column in the WHERE clause (e.g., UPPER(column_name)), a function-based index on that expression can improve performance.
		--When Performance Bottlenecks Are Identified - If specific queries are performing poorly and involve large tables or complex filtering/sorting, analyzing the execution plan can reveal opportunities for index creation.

	--subquery that references columns from the outer, or parent, query
	--subquery cannot be executed independently and must be evaluated once for each row processed by the parent statement.

		--This is typically seen in the WHERE clause of the subquery, where a column from the outer query's table is compared to a column within the subquery's table.
	--Row-by-Row Execution: Due to this dependency, the correlated subquery is re-executed for each row returned by the outer query.
	--performance Considerations -correlated subqueries can be less efficient than alternatives like joins or analytic functions, especially on large datasets, due to their repeated execution. 
		--Oracle's optimizer may sometimes rewrite correlated subqueries as joins for better performance.

		--All savepoints within the transaction are erased.
		--Transaction locks are released.
		--The changes cannot be undone using ROLLBACK.

--Oracle hints
	--Hints are instructions that you add to a SQL statement that tell the data source query optimizer the most efficient way to run the statement. 	
	--Hints override the optimizer's processing plan, so you can use hints to improve performance by forcing the optimizer to use a more efficient plan.
	--Types of Hints:
		--Optimizer Hints: Influence the overall optimization goal (e.g., ALL_ROWS, FIRST_ROWS).
		--Access Path Hints: Direct the optimizer to use specific access methods (e.g., INDEX, FULL, NO_INDEX, ROWID).
			--FULL -forces a full table space, example =>SELECT /*+ FULL(e) */ employee_id, last_name FROM hr.employees e WHERE last_name LIKE 'S%';
			--INDEX - tells optimizer to use a specific index, example=> SELECT /*+ INDEX(employees emp_department_ix) */ employee_id, department_id FROM employees WHERE department_id > 50;
			--LEADING - specifies the order in which tables should be joined, example=> SELECT /*+ LEADING(e d) */ e.name, d.location FROM employees e JOIN departments d ON e.department_id = d.id;

		--Join Order Hints: Specify the order in which tables should be joined (e.g., ORDERED).
		--Join Method Hints: Suggest a particular join algorithm (e.g., USE_NL, USE_MERGE, USE_HASH).
			--USE_NL (use nested loops) - suggest the optimizer use a nested loop join method, example => SELECT /*+ USE_NL(d) */ e.employee_id, d.department_name FROM employees e, departments d WHERE e.department_id = d.department_id;	
			--USE_MERGE
			--USE_HASH
		--Parallel Execution Hints: Control the degree of parallelism for a statement or object (e.g., PARALLEL, NO_PARALLEL).
			--PARALLEL - instructs optimizer to execute the query against the sales table using 4 parallel processes, example=>SELECT /*+ PARALLEL(sales 4) */  FROM sales;		
		--Query Transformation Hints: Influence how the optimizer transforms the query (e.g., MERGE, NO_MERGE, STAR_TRANSFORMATION).
--parallelism in queries
	--Using SQL Hints (Statement Level)The most common way to trigger parallelism is by adding a PARALLEL hint directly into your SELECT statement.
	--Specify a Degree of Parallelism (DOP) -sql => SELECT /*+ PARALLEL(4) */ * FROM large_table;
		--This instructs Oracle to use exactly 4 parallel execution processes.
	--Let Oracle Decide - sql =>SELECT /*+ PARALLEL */ * FROM large_table;
		--Oracle will automatically determine the best number of processes based on your hardware and current load.
	--Setting Table Properties (Object Level)You can define a default parallelism for a specific table so that any query hitting that table runs in parallel automatically.
		--Enable Parallelism - sql => ALTER TABLE large_table PARALLEL 4;
		--Disable Parallelism - sql => ALTER TABLE large_table NOPARALLEL;
	--Forcing Session-Wide Parallelism - If you want every query in your current session to run in parallel without modifying individual SQL statements, use the ALTER SESSION command.
		--Force Parallel Query - sql => ALTER SESSION FORCE PARALLEL QUERY;
		--For DML Operations (Insert/Update/Delete): Parallel DML is often disabled by default. You must enable it explicitly for the session.
			--sql => ALTER SESSION ENABLE PARALLEL DML;
	
	--When to Use Parallelism
		--Parallelism is most effective when:
			--Scanning very large tables (millions of rows).--
			--Performing complex joins or aggregations (GROUP BY).
			--The system has underutilized CPUs and high I/O bandwidth.
			--The environment is low-concurrency (e.g., batch processing or data warehousing).
		Note1: Avoid using parallelism for small, fast queries (OLTP), as the overhead of coordinating multiple processes can actually make them slower. 
		Note2: You can monitor active parallel processes using the V$PX_PROCESS view
		RAC Note3: view session parameters for parallelism in view V$SES_OPTIMIZER_ENV
--oracle optimizer
	--the optimizer turns a SQL statement into an execution plan
	--evaluates alternatives such as join order and method, access paths, parallel execution, and query rewrites 
	--chooses the plan with the best expected performance based on optimizer statistics, metadata, and enabled features.
	--Two concepts drive most decisions:
		--Selectivity: the estimate of how much a WHERE-clause predicate filters down the number of rows returned.
			--rac note: this is number of rows returned
       --Cardinality: how many rows are predicted to flow through each operation performed by the SQL statement.
			--rac note: this is the number of unique values a column has
	--optimizer considerations
		--Which table becomes the driving row source.
        -- What types of joins to use, for example, nested loops, hash joins, or sort-merge joins.
			--For multi-table SQL statements, the optimizer has two major degrees of freedom:
				--Join order =>The optimizer determines an order in which row sources are combined, based heavily on estimated cardinalities and selectivities.
				--Join method
					--Oracle commonly chooses among:
						--Nested loops (often strong for selective lookups).
						--Hash joins (often strong for larger joins, especially where hashing fits memory).
						--Sort-merge joins (useful in some ordered/mergeable cases).
					--At a conceptual level: join order decides what drives, join method decides how to combine.
        -- How to access data, for example, via a full table scan, index scan, or partition pruning.
			--Data Access: Access Paths and Storage-Aware Choices
				--The optimizer chooses among multiple access paths, influenced by schema design and data organization. 
				--At a high level, it considers:
					--Index and table access options
						-- Index-based access (various scan styles)
						--Full scans when a large portion of rows is needed or when scanning is cheaper than many random I/Os
					-- Partitioning-aware optimization
						--When tables are partitioned, the optimizer can take advantage of:	
							--Partition pruning (limit work to relevant partitions)
							--Partition-wise strategies (in certain join/grouping scenarios)
							--Local vs. global index implications
						--Partitioning and indexing don’t just change storage; they expand the optimizer’s set of viable strategies.					
       -- When to apply parallel execution and how to distribute work.	
	--Oracle applies query transformations before and during plan selection
		--transformations are rewrites that preserve correctness but change the internal shape of the query so it can be executed more efficiently.
		--types of transformations are
		--Subquery transformations (e.g., unnesting)
		--View merging and predicate pushing
		--Join transformations
		--Aggregation transformations
		--Set-to-join and related rewrites
	--optimizer stats include
		--Table stats: row counts, block counts, average row length.
		--Index stats: levels, leaf blocks, clustering factor, distinct keys.
		--Column stats: distinct values, null counts, distribution information.
		--Histograms (when appropriate): represent skewed distributions so selectivity can be estimated more accurately.
		--Extended statistics (e.g., column groups): help with correlated columns and multi-column selectivity.	
	--SQL Plan Management =>mechanism that enables the database to maintain stable yet optimal performance for SQL statements
		--works by ensuring that the Oracle optimizer only uses execution plans that have been previously verified or "accepted" into a SQL Plan Baseline
		--SPM consists of three main operational phases: 
			--Plan Capture: This phase makes the database aware of execution plans. It can be automatic by setting OPTIMIZER_CAPTURE_SQL_PLAN_BASELINES to TRUE, which records repeatable SQL statements (those executed at least twice).
			--Plan Selection: When a statement is hard parsed, the optimizer builds a best-cost plan. If a baseline exists, the optimizer compares the new plan against it. If the new plan is not in the baseline, it is marked as "unaccepted" in the plan history, and the optimizer reverts to an existing accepted baseline plan.
			--Plan Evolution: This is the process of adding new, better-performing plans to the baseline. The database verifies that unaccepted plans perform at least as well as currently accepted plans before promoting them. 
		--Key tools and parameters used for managing SPM include:
			--DBMS_SPM Package: The primary PL/SQL interface used to load, evolve, and drop plan baselines. Common functions include LOAD_PLANS_FROM_CURSOR_CACHE, EVOLVE_SQL_PLAN_BASELINE, and PACK_STGTAB_BASELINE.
			--SQL Management Base (SMB): A logical repository located in the SYSAUX tablespace that stores plan history, baselines, and logs.
			--Automatic SPM (ASPM): Introduced in Oracle 19c, this uses a background task (SYS_AUTO_SPM_EVOLVE_TASK) to automatically identify regressions, test alternate plans, and enforce the best ones without manual intervention.
			--Fixed Plans: A baseline plan can be marked as "FIXED", giving it preference over non-fixed plans and preventing the automatic addition of new plans to the baseline
		--Key Benefits
			--Regression Prevention: Minimizes performance drops during database upgrades, optimizer version changes, or schema modifications (e.g., adding an index).
			--Graceful Adaptation: Allows the system to gradually adopt better plans as data distribution changes, provided they pass verification.
			--Manual Control: Enables DBAs to manually force a specific "good" plan from AWR or the cursor cache to fix immediate performance issues.	
	--SPM Monitoring Views - Use the following views to monitor your SQL plan baselines:
		--DBA_SQL_PLAN_BASELINES: Displays details about stored plans, including whether they are accepted, enabled, or fixed.
		--DBA_SQL_MANAGEMENT_CONFIG: Shows configuration settings like space budget and retention period.
		--DBMS_XPLAN.DISPLAY_SQL_PLAN_BASELINE: A utility function to display the actual execution steps for a baseline plan.			
--join methods - is the mechanism for joining two row sources
	--Depending on the statistics, the optimizer chooses the method with the lowest estimated cost. 
	--whole lotta info at https://docs.oracle.com/en/database/oracle/oracle-database/18/tgsql/joins.html#GUID-A2DA6A1E-6180-4AB9-A777-586AF3953D53
	--Nested Loops Joins - 
		--join an outer data set to an inner data set.
			--For each row in the outer data set that matches the single-table predicates, the database retrieves all rows in the inner data set that satisfy the join predicate. 
				--If an index is available, then the database can use it to access the inner data set by rowid.
		--In general, nested loops joins work best on small tables with indexes on the join conditions. 
		--If a row source has only one row, as with an equality lookup on a primary key value (for example, WHERE employee_id=101), then the join is a simple lookup. 
		--The optimizer always tries to put the smallest row source first, making it the driving table.
		--The number of rows expected from the join is what drives the optimizer decision, not the size of the underlying tables.
			--For example, a query might join two tables of a billion rows each, but because of the filters the optimizer expects data sets of 5 rows each.
		--The number of iterations of the inner loop depends on the number of rows retrieved in the outer loop. 
			--For example, if 10 rows are retrieved from the outer table, then the database must perform 10 lookups in the inner table. 
			--If 10,000,000 rows are retrieved from the outer table, then the database must perform 10,000,000 lookups in the inner table.	
		--The outer loop appears before the inner loop in the execution plan (good to know)	
		--For every fetch request from the client, the basic process is as follows:
			--Fetch a row from the outer row source
			--Probe the inner row source to find rows that match the predicate criteria
			--Repeat the preceding steps until all rows are obtained by the fetch request
	--hash joins - database uses a hash join to join larger data sets.
		--optimizer considers a hash join when a relatively large amount of data must be joined (or a large percentage of a small table must be joined), and the join is an equijoin
		--hash join is most cost effective when the smaller data set fits in memory.

				--1. Performance and Scalability
					--Reduced Hard Parsing: When literals (e.g., WHERE id = 5) are used, Oracle must perform a "hard parse" for every unique value to generate an execution plan. Bind variables (e.g., WHERE id = :id) allow Oracle to "soft parse" by reusing an existing execution plan from the library cache.
						--elements of hard parsing (required after library cache miss)
						-- When a SQL statement is submitted, Oracle checks if it exists in memory. If not, 
							--it performs a syntax check (valid SQL), 
							--semantic check (objects/privileges exist), 
							--and optimization (generating the execution plan).
						--soft parsing (aka libary cache miss) - occurs when a matching, previously parsed statement is found in the cache, allowing it to be reused, which is much faster.	
					--Shared Pool Efficiency: Instead of flooding the shared pool with thousands of near-identical queries, bind variables ensure only one "parent cursor" is stored for multiple executions.
					--Lower CPU and Memory Usage: Soft parsing consumes far fewer resources than hard parsing, which is critical in high-volume Online Transaction Processing (OLTP) environments.
					--Reduced Latch Contention: Hard parsing requires serialization through internal locking mechanisms called latches. By using bind variables, you minimize contention for these latches, allowing more users to access the system simultaneously.
				--2. Enhanced Security
					--Prevention of SQL Injection: Bind variables are the most effective way to prevent SQL injection attacks. Because the data is never treated as part of the executable SQL statement during parsing, malicious input cannot alter the query's structure.
					--Automatic Data Masking: Bind variable values may be handled differently in error messages or logs, providing a layer of compliance and data protection.
				--3. Application Development Benefits
					--Simplified Coding: You do not need to manually escape problematic characters (like single quotes) in your code because the database treats the bind value as data, not as part of the command string.Named 
					--Binding: Platforms like Python or Java allow binding by name (e.g., :dept_id), which makes code more readable and allows the same value to be repeated in a statement while only being supplied once.
					--Directional Binding: Oracle supports IN, OUT, and IN OUT bind variables, allowing applications to pass data to the database and retrieve modified results or return values from PL/SQL blocks efficiently.

The Informative Way: Using RAISE_APPLICATION_ERRORIf you need to transform a generic database error (like an Oracle ORA-01403: no data found) into a user-friendly custom error message for a front-end application, you use RAISE_APPLICATION_ERROR. 	--Key Reasons to Re-Raise an Exception
		--Logging and Auditing: You need to record that an error happened at a specific point in your application before letting it propagate up. 		--Resource Cleanup: If your local code opens an external resource—such as a file via UTL_FILE or a network connection—an error will leave that resource hanging. You trap the error to close the file handle or release the resource, and then immediately re-raise the exception so the transaction still fails properly.
		--Transaction Rollbacks: You may want to roll back a specific, isolated set of operations within a local sub-block or savepoint. After executing the local ROLLBACK, you re-raise the exception to alert the master routine that the subset of data failed to process.P
		--reventing "Error Swallowing" (Anti-pattern Mitigation): Using a generic WHEN OTHERS block without a re-raise is highly dangerous. --what is a transaction => A transaction is a logical, atomic unit of work that contains one or more SQL statements.
	--statements in a transaction are either permanently applied (committed) or completely undone (rolled back) together, preventing incomplete operations and maintaining the database's correct state, even if an application fails. 
--difference between Commit, Rollback, and Savepoint?
	--Commit: This ends the current transaction by ensuring that all pending data changes are made permanent.
	--Rollback: This ends the current transaction by discarding or deleting all pending data changes.
	--Savepoint: It divides a transaction into smaller parts. You can rollback the transaction until you find a particular named savepoint.
--savepoint - technique to divide a transaction into multiple parts so the user can rollback the transaction up to a specified point	
	--using Save Point we can roll back a part of a transaction instead of the entire transaction.
	--Whenever a user creates SAVEPOINT within the transaction then internally system is allocating a special memory for a SAVEPOINT and storing the 
transaction information which we want to roll back (cancel).

--for update clause - used within a select statement to explicitly lock the selected rows for the duration of the current transaction
	--prevents other transactions from modifying those specific rows until the current transaction either commits or rolls back;
	--useful for an transactional workload where multiple transactions might attempt to access the same rows at the same time
	--lets you base an update on the existing values in the rows because it ensures that no other user can change those values before you update
		--example=>set column_name = column_name + 5 => this adding 5 to the existing value works because column name has not been updated before you run your update
	--locking behavior modifiers
		--skip locked - skips rows that are currently locked by other sessions and only returns unlocked rows
		--nowait - returns an error immediately if a lock cannot be acquired
		--wait n - waits for n seconds to acquire the lock before returning an error

--What is pragma in Oracle PL/SQL?

	--refers to the compiler directive and it is used to provide an instruction to the compiler.

	--Common Oracle Pragmas

			-- most frequent use of this behavior is for logging: 
				--A main transaction starts complex data processing.
				--An error occurs.

--parts of a database trigger	
	--Trigger Name - A unique identifier for the trigger within its schema.
	-- Triggering Event - The specific action or event that causes the trigger to fire. This can be: 
		--DML Statements: INSERT, UPDATE, or DELETE operations on a table or view. 
		--DDL Statements: CREATE, ALTER, or DROP operations on schema objects.
		--Database System Events: Such as STARTUP, SHUTDOWN, LOGON, LOGOFF, or system errors.
	--Trigger Timing - Specifies when the trigger action should execute relative to the triggering event:
		--BEFORE: The trigger fires before the triggering event.

		--Logon Triggers - These are invoked when a user logs into the database, and are often used for controlling database access and monitoring user activity.

		--Row-Level Triggers - The trigger's action executes once for each row that is affected by the triggering event.
		--Statement-Level Triggers - The trigger's action executes only once for the entire SQL statement, regardless of how many rows are affected.

	--Compound Triggers: A single trigger that can execute logic at multiple timing points (e.g., BEFORE statement, AFTER row)

--How do you troubleshoot a slow-running query?  (I think this is a HUGE interview question)
	--Analyze the Execution Plan
		--Use EXPLAIN PLAN or DBMS_XPLAN.DISPLAY to view the query's execution plan. 
			--This reveals how Oracle intends to execute the query, including join methods, access paths (e.g., full table scans, index scans), and estimated costs.
			--Look for inefficient operations like full table scans on large tables, excessive sorts, or nested loops with large outer tables.
	--Examine Statistics and Indexes:
		--Table and Index Statistics: Ensure statistics for tables and indexes involved in the query are up-to-date. 
			--Outdated statistics can lead the optimizer to choose suboptimal execution plans. Use DBMS_STATS.GATHER_TABLE_STATS to update them.
		--Indexes: Verify that appropriate indexes exist on columns used in WHERE clauses, JOIN conditions, ORDER BY clauses, and GROUP BY clauses. 
			--Create new indexes or modify existing ones if necessary.
			--Index Usage: Check if indexes are actually being used by the query as expected in the execution plan.		
	--Review SQL Code:
		--Simplicity and Efficiency: Simplify complex queries where possible. Avoid unnecessary subqueries or UNION operations if a simpler JOIN or OR condition can achieve the same result.
		--Filtering: Ensure WHERE clauses are selective and filter data early in the execution process to reduce the amount of data processed.
		--Join Conditions: Verify that join conditions are correct and efficient. Using appropriate join types (e.g., INNER JOIN, LEFT JOIN) can impact performance.
		--Data Types: Ensure consistent data types between joined columns to avoid implicit conversions that can hinder index usage.
			--rac note: make sure you are joinining columns of the same data type.  If not, index will not be used
	--Monitor System Resources:
		--CPU, I/O, Memory: Monitor database server resources during query execution. High CPU usage, excessive disk I/O, or memory contention can indicate bottlenecks.
		--Locks: Check for database locks or blocking sessions that might be preventing the query from proceeding efficiently		
	--Utilize Oracle Tuning Tools:
		--SQL Tuning Advisor: Use Oracle's SQL Tuning Advisor to get recommendations for improving query performance, such as creating new indexes, restructuring SQL, or creating SQL profiles.
		--ASH/AWR Reports: Analyze Active Session History (ASH) or Automatic Workload Repository (AWR) reports to identify top wait events and resource-intensive SQL statements.
	--Test and Compare (usefule when implementing query changes)
		--Baseline: Establish a baseline performance for the query when it's running optimally.
		--Test Changes: Implement changes one at a time and re-test the query to measure the impact on performance. Compare new execution plans and performance metrics against the baseline.
--describe components of the physical and logical database structure."
	--Physical Structures:
		--Data Files - These files store the actual data of the database, including tables, indexes, and other database objects. They are stored on disk.
		--Redo Log Files - These files record all changes made to the database, ensuring data recoverability in case of failure. They are crucial for instance and media recovery. 
		--Control Files - These small, binary files are essential for database operation. They contain metadata about the database's physical structure, such as the names and locations of data files and redo log files, and the current database state.
	--Logical Structures:
		--Data Blocks - The smallest unit of logical storage in an Oracle database. Data blocks correspond to physical blocks on disk and are used to store rows of data.
		--Extents - A logical unit of storage consisting of a CONTIGUOUS SET OF DATA BLOCKS (remember this). When a segment needs more space, it allocates a new extent.
		--Segments - A logical storage unit that contains all data for a specific database object, such as a table, index, or undo segment. A segment can span multiple extents.
			--Non-partitioned tables and indexes - Typically, a non-partitioned table has one data segment, and a non-partitioned index has one index segment.
			--Partitioned tables and indexes - For partitioned tables and indexes, each partition is stored in its own segment. Therefore, a partitioned table or index will consist of multiple segments, one for each partition.
		--Tablespaces - The primary logical storage unit in an Oracle database. A tablespace can contain multiple segments and is mapped to one or more data files. Tablespaces provide a way to organize and manage database objects and their storage.
		--Schema Objects - Logical structures owned by a database user, including tables, views, indexes, sequences, procedures, and functions. These objects define the structure and behavior of the data within the database.	
--difference between a stored procedure and a function in oracle - both stored procedures and functions are named PL/SQL blocks that can be stored in the database and reused. 
	--they differ primarily in their purpose and how they handle return values
		--functions are designed to compute and return a value, while procedures are designed to perform actions and potentially modify data.	
	--Return Value 
		--function must return a single value. This value can be of any valid PL/SQL data type.
		--procedure does not necessarily return a value. It can return values through OUT or IN OUT parameters, but a direct return statement is not required or used to return a single value like a function.
	--Usage in SQL
		--functions can be called directly within SQL statements (e.g., SELECT function_name(...) FROM dual; or as part of a WHERE clause).
		--procedures cannot be called directly within SQL statements. They are executed using the EXECUTE command or by calling them from other PL/SQL blocks.
	--Data Manipulation Language (DML) Operations:
		--functions are designed to perform calculations and retrieve data without modifying the database state.

--chained row
	--when a single row of a table is too large to fit entirely within a single database block. necessitates Oracle to store the row's data across multiple blocks, creating a "chain" of blocks that contain the complete row.
	--common with tables containing LOB (Large Object) data types such as BLOB, CLOB, LONG, or LONG RAW
	--also tables with a very high number of columns (e.g., more than 255) can also lead to chaining, as Oracle internally breaks down wide tables into pieces.
	--Chained rows can negatively impact query performance, especially when accessing rows via an index. 
		--If the index points to the first block of a chained row, Oracle needs to perform additional I/O operations to read all the subsequent blocks in the chain to reconstruct the complete row. 
		--Full table scans are generally less affected by chained rows because Oracle will eventually encounter all the blocks containing the row's pieces during the scan.
--migrated row - occurs when an update to an existing row causes it to become too large to fit in its original block, leading Oracle to move the entire row to a new, larger block while leaving a "forwarding address" in the original block. 	
	--migrated rows are bad because
		Degraded Performance - For index-based lookups, an additional I/O is needed. The index provides the address of the original block, but that block then redirects to the new block where the actual data is stored. 
		--Increased I/O Operations - The extra step of following the forwarding pointer increases the workload and can slow down queries. 
		--Block Fragmentation - Row migration can contribute to fragmented blocks and inefficient use of storage. 
	--How to prevent migrated rows
		--Tune PCTFREE and PCTUSED - These parameters can be adjusted to ensure sufficient free space is reserved within blocks for future updates, minimizing the need for rows to move. 
		--Consider Database Design - A table design that allows for excessively large rows increases the likelihood of migration.

--distributed database system
	--collection of physically dispersed Oracle databases that function as a single logical database to applications.
	--Key characteristics and components include:
		--Sharding: This is a core concept where a single logical database is physically divided into multiple independent databases called "shards." 
			--Each shard runs on its own hardware and does not share resources with other shards (shared-nothing architecture). 
			--This enables linear scalability and fault isolation.
		--Data Distribution: Data can be distributed across shards using various strategies like hash, range, list, or composite sharding keys, or even value-based methods to meet specific requirements like data residency regulations.
	
		--Replication: Data within each shard is typically replicated for survivability and high availability, enabling an active-active architecture where all shards can process application requests.
		--Transparency to Applications: The physical distribution of data is hidden from applications. Applications interact with the globally distributed database as if it were a single, centralized database, simplifying development and management.
		--Distributed Query Processing and Transaction Management: The system automatically handles queries and transactions that span multiple shards, ensuring data consistency across the distributed environment.
		--Deployment Options: Oracle's distributed database capabilities are available in various environments, including Oracle Cloud Infrastructure (OCI) as automated services (like Globally Distributed Autonomous Database), as well as in multicloud and on-premises deployments.

	--Use DATE when you only need second-level precision and do not require time zone awareness or fractional seconds. This is suitable for older applications or when storage efficiency is a primary concern and higher precision is unnecessary.
	--Use TIMESTAMP when you need higher precision (fractional seconds) or require time zone handling.
		--Choose TIMESTAMP WITH TIME ZONE if you need to preserve the original time zone information of the data. 
			--rac note: international dates/times will remain as they are entered( i.e., time zone is unchanged and the date/time is unchanged)
		--Choose TIMESTAMP WITH LOCAL TIME ZONE if you want Oracle to automatically handle time zone conversions between the database and user sessions.
			--rac note: international dates/times will automatically convert to the local time zone
				--(so a value entered as 12 noon on 1/1/2000 GMT will convert to 6PM on 12/31/1999 => because central time is -6 UTC)
	--key differences
		--precision
			--DATE stores date and time down to the nearest second. It does not support fractional seconds.
			--TIMESTAMP can store date and time with fractional seconds, up to nanosecond precision (depending on the specified precision, e.g., TIMESTAMP(6) for microseconds).
		--time zone info	
			--DATE does not store any time zone information. It represents a specific point in time without knowledge of the time zone in which it was recorded.
			--TIMESTAMP can be extended to include time zone information:
				--TIMESTAMP WITH TIME ZONE: Stores the date and time along with the time zone offset or region name.
				--TIMESTAMP WITH LOCAL TIME ZONE: Stores the date and time, and automatically converts it to the database time zone when stored and to the session time zone when retrieved.

--what is a package cursor - cursor that is declared and defined within a PL/SQL package.
	--Key characteristics of package cursors:
		--Declaration in Package Specification - package specification declares the cursor, making it visible and accessible to applications and other PL/SQL units that have privileges on the package. The specification typically includes the cursor's name and its RETURN clause, which defines the data type of the rows returned by the cursor.
		--Definition in Package Body - actual SQL SELECT statement that the cursor executes is defined in the package body. This separation allows for information hiding and provides flexibility, as the cursor's query can be changed in the package body without altering the package specification, thus not affecting external code that uses the cursor.
		--Scope and Lifetime - When a packaged cursor is opened, it remains open until explicitly closed or until the session disconnects. This differs from local cursors within a PL/SQL block, which are typically closed when the block exits.
		--Referencing - Packaged cursors are referenced using dot notation, for example, package_name.cursor_name.
	Benefits:
		--Modularity and Reusability: Grouping cursors within packages promotes code organization and allows for easy reuse across different parts of an application.
		--Information Hiding - implementation details (the actual SELECT statement) of a cursor can be hidden within the package body, making the code more maintainable and protecting the integrity of the package.
		--Centralized Management - Cursors related to a specific business logic or data entity can be managed in a single package.

--What are ACID properties in SQL?
	--acronym representing four key properties of database transactions: Atomicity, Consistency, Isolation, and Durability. 
	--properties ensure that database transactions are processed reliably and maintain data integrity, even in the event of errors or system failures. 
	--Atomicity:This property ensures that a transaction is treated as a single, indivisible unit of work. All operations within a transaction must either complete successfully, or none of them do. 
		--If any part of the transaction fails, the entire transaction is rolled back, leaving the database in its original state before the transaction began.
	--Consistency:Consistency guarantees that a transaction brings the database from one valid state to another. 
		--This means that all data integrity rules, constraints, and triggers defined in the database must be satisfied both before and after the transaction. 
		--If a transaction would violate any of these rules, it is aborted, and the database reverts to its previous consistent state. 
	--Isolation:Isolation ensures that concurrent transactions do not interfere with each other. 
		--Each transaction appears to execute in isolation, as if it were the only transaction running on the database. 
		--This prevents issues like dirty reads, non-repeatable reads, and phantom reads, ensuring that the outcome of multiple concurrent transactions is the same as if they were executed sequentially.
			--oracle prevents dirty reads by using multi-version concurrency control where all data read by a query comes froma single point in time preventing the observation of uncommited data from other transactions
			--Oracle prevents phantom reads by using the serializable transaction isolation level.
				--in serializable mode, a transaction sees the database as it existed at the single point in time when the transaction began. This "snapshot" of the database is consistent for all queries within that transaction, ensuring that no new rows can appear (or "phantom" read) during its execution. 
	--Durability:Durability guarantees that once a transaction has been committed, its changes are permanently stored and survive any subsequent system failures, such as power outages or crashes. 
		--is typically achieved through techniques like write-ahead logging or storing data on non-volatile storage, ensuring that committed data is never lost.

--index benefits and drawbacks - accelerate data retrieval by providing direct paths to table rows but introduce overhead by consuming disk space and slowing data modification (INSERT, UPDATE, DELETE) because the index must be updated with each change to the indexed data.
	--Benefits of Oracle Indexes
		--Faster Data Retrieval:Indexes provide a fast path to locate specific rows without requiring a full table scan, significantly speeding up SELECT queries. 
		--Improved Performance for Sorting and Grouping: By pre-sorting data in an index, queries that involve ORDER BY or GROUP BY clauses can execute more efficiently. 
		--Maintaining Data Integrity: Unique indexes automatically ensure that no duplicate values are entered into the indexed column(s), helping to maintain data integrity. 
		--Support for Complex Queries: Function-based indexes allow you to precompute and store the results of expressions, making queries that use these functions faster. 
		--Independence from Base Tables:Indexes are separate schema objects that can be created, dropped, or modified without affecting the base tables or other database objects. 
	--Drawbacks of Oracle Indexes
		--Increased Storage Space: Indexes themselves are data structures that require physical disk space for storage, which can be significant with many large tables and indexes. 
		--Slower Data Modification (DML): When you INSERT, UPDATE, or DELETE data in a table, all relevant indexes must also be updated, adding processing overhead and reducing DML performance. 
		--Management Overhead: As data and applications change, indexes can become less useful or even detrimental. You may need to revisit, modify, or drop indexes, which requires an understanding of the data model and query patterns. 
		--Potential for Overuse: Adding too many indexes to a table can be counterproductive, leading to increased storage costs and excessive DML overhead without necessarily improving overall query performance. 
		--Optimizer Reliance: The Oracle optimizer determines whether to use an index based on its cost-based optimization. For certain index types, like function-based indexes, the index might not be used until it is analyzed and the database is aware of its presence. 
--differences between clustered and non-clustered indexes
	--a clustered index physically sorts and stores the table's data rows in the order of the indexed column, 
		--clustered index is conceptually and functionally equivalent to an Index-Organized Table (IOT)
	--a non-clustered index is a separate structure containing index key values and pointers to the data rows, which remain in their original physical order. 
		--A table can have only one clustered index, but multiple non-clustered indexes, and clustered indexes offer faster retrieval for range scans as data is stored together, whereas non-clustered indexes are better for accessing specific rows quickly without modifying the table's physical storage order. 
	--Clustered Index - same as Index-Organized Table (IOT)
		--Physical Storage:Sorts and stores the actual data rows in the table based on the indexed columns, physically arranging the data. 
		--Number per Table: Only one clustered index can exist per table because the table's data can only be stored in one physical order. 
		--Leaf Nodes: The leaf nodes of a clustered index are the data pages themselves. 
		--Data Retrieval: Faster for sequential or range-based queries because related data is stored contiguously.
		--Use Cases: Ideal for primary keys or columns frequently used in range-based queries or sorted in a specific order.
		--Space: Does not require additional disk space because it uses the existing table data. 	
		
	--Non-Clustered Index
		--Physical Storage: Creates a separate structure from the data rows with the index keys and pointers to the actual data rows. 
		--Number per Table: Multiple non-clustered indexes can be created on a single table. 
		--Leaf Nodes: The leaf nodes contain index key values and pointers to the data rows, not the data itself. 
		--Data Retrieval: Faster for retrieving specific rows based on an index key, but requires a lookup to find the data. 
		--Use Cases: Useful for speeding up queries on non-primary key columns or columns that are frequently filtered. 
		--Space: Requires additional disk space because it stores a separate copy of the indexed columns and pointers

--types of oracle indexes
	--B-Tree Indexes: These are the most common index type, suitable for a wide range of scenarios. Learn how to create, maintain, and use B-Tree indexes.
		--B-Tree is short for balanced tree
		--organized in a hierarchical, balanced tree structure. 
			--balance ensures that the path from the root to any leaf node is roughly the same length, leading to consistent query performance.
		--Branch Blocks and Leaf Blocks: The index consists of two main types of blocks:
			--Branch Blocks: These blocks form the upper levels of the tree and are used for navigation. 
				--contain keys and pointers to lower-level index blocks (either other branch blocks or leaf blocks), guiding the search towards the desired data. 
				--The root block is the topmost branch block.
			--Leaf Blocks: These blocks are at the lowest level of the tree and store the actual indexed data. 
				--Each leaf block contains sorted index key values and the corresponding ROWIDs (Row Identifiers) of the rows in the table where those key values are found.
		--searching: When a query uses an indexed column, Oracle traverses the B-tree. 
			--It starts at the root branch block, comparing the search key with the keys in the branch block to determine which child block to follow.
			--process continues down through the branch blocks until the appropriate leaf block is reached. 
			--Once in the leaf block, the sorted key values allow for efficient location of the matching key and its associated ROWID.
		--Data Access: The retrieved ROWID from the leaf block provides Oracle with the exact physical location of the data row in the table, enabling direct and fast access to the required data.
		--Key Benefits: 
			--Efficient Data Retrieval: B-tree indexes significantly speed up queries that involve exact matches, range searches, and sorting on indexed columns.
			--Support for Primary Keys: They are particularly well-suited for primary key columns, which are typically unique and frequently used in searches.
			--High-Cardinality Columns: B-tree indexes are effective for columns with a high number of distinct values (high cardinality).
	--Bitmap Indexes: Ideal for columns with low cardinality, bitmap indexes can significantly speed up certain queries. Understand when and how to employ them.
	--Function-Based Indexes: Discover how to create indexes on expressions or functions, allowing for indexed searches on computed values.
	--Index-Organized Tables (IOTs): Explore the concept of IOTs, which store data within an index structure, saving storage space and improving query performance.

--shared pool latch contention
	--rac note: it seems a latch is an attempt by oracle to reserve (or put a lock on) a segment of memory for its purposes and then releases the latch
		--when there is no memory available, processes have to wait for it to become available
	--performance issue where multiple sessions are competing for access to the same shared memory structures within the shared pool
	--results in performance degradation and increased cpu utilization
	--causes
		--excessive hard parsing - most common cause, occurs when applications use literal values in sql queries instead of bind variables
		--inadequate shared pool sizing - if shared pool is too small, frequently used sql statements and data dictionary info may be prematurely aged out and reloaded, leading to more parsing and latch activity
		--inefficient use of shared pool resources - apps/processes that generate a large number of unique, non sharable sql statements can exhause shared pool resources and increase latch contention
	--resolution strategies
		--implement bind variables - modify code to use bind variables for all dynamic sql statements allowing Oracle to reuse parsed sql statement, significantly reducing hard parsing and shared pool latch contention
		--identify and tune objects - analyze awr reports and v$latch stats to identify specific latches experiencing high contetion and the correspondin objects of sql statements involved
		--optimize shared pool size - ensure the SHARED_POOL_SIZE initialization parameter is adequately configured to accommodate the working set of sql statements and data dictionary info
			--monitor shared pool statistics to identify potential sizing issues
		--reduced libray cache reloads - aim for a high library cache hit ratio by promoting sql sharing and ensuring the shared pool is large enough to retain frequently accessed objects
		-consider multi threaded server - using oracle's shared server architecture can influence shared pool latch usage although it is not a universal solution for all contention issues

--pipelined function - special type of pl/sql table function designed to return rows interactively similar to how a select statement retrieves data from a table
	--better definition =>special type of PL/SQL function designed to return a collection of data in a streaming fashion, rather than returning the entire collection at once.
	--advantages
		--Iterative Row Return: Unlike standard table functions that return an entire collection at once, pipelined functions return rows one by one as they are produced. 
			--allows the calling query to start processing results immediately, without waiting for the entire collection to be built in memory.
		--Reduced Memory Consumption: By avoiding the need to store the entire result set in a collection before returning it, pipelined functions significantly reduce the memory footprint, especially when dealing with large datasets.
		--Improved Performance: The iterative nature of pipelined functions can lead to better performance, as the producer and consumer of data can operate concurrently. 
			--particularly beneficial in scenarios where the function performs complex computations or fetches data from external sources.
		--Virtual Table Behavior: Pipelined functions can be queried directly in the FROM clause of a SELECT statement using the TABLE operator, making them behave like virtual tables. This allows for seamless integration into SQL queries.
		--PIPE ROW Statement: Inside a pipelined function, the PIPE ROW statement is used to return individual rows to the calling query. This statement immediately sends the specified row and allows the function to continue processing the next row.
		--NO_DATA_NEEDED Exception: If the calling query terminates before the pipelined function has produced all its rows (e.g., due to a WHERE ROWNUM <= N clause), Oracle raises the NO_DATA_NEEDED exception. This allows the function to gracefully stop processing and release any resources.
		--Declaration: A pipelined function is declared using the PIPELINED keyword in its header, and its return type must be a collection type (e.g., VARRAY or nested table) defined at the schema level or within a package.

--System Change Number (SCN) is a logical, internal time stamp used by Oracle Database to track and order events within the database. 
	--ensures data consistency, supports recovery, and fulfills the ACID properties of transactions
	--Key characteristics and uses of SCNs:
		--Logical Time Stamp: SCNs represent a point in time within the database, but they are not directly tied to wall-clock time.
		--Ensuring Consistency: SCNs are crucial for maintaining read consistency, allowing users to see a consistent view of data even while other transactions are modifying it.
		--Transaction Ordering: They order events that occur within the database, providing a chronological record of changes.
		--Recovery: SCNs play a vital role in database recovery, marking points in time to determine which changes need to be applied or rolled back.
		--Flashback Features: SCNs are fundamental to Oracle's Flashback features, such as Flashback Query and Flashback Version Query, enabling users to view data as it existed at a specific SCN or timestamp.
		--Structure: An SCN is a 6-byte number composed of two parts: SCN_WRAP (16 bits) and SCN_BASE (32 bits), which work together to ensure a continuously incrementing value.
	--Oracle provides functions to convert between SCNs and timestamps:
		--SCN_TO_TIMESTAMP(scn): Returns the approximate timestamp associated with a given SCN. 
		--TIMESTAMP_TO_SCN(timestamp): Returns the approximate SCN associated with a given timestamp.

--Codd's rules -set of 12 principles proposed by Edgar F. Codd to define what constitutes a relational database management system (RDBMS).
	--core principles of Codd's rules
		--The Information Rule: All information must be stored logically in tables. 
		--The Guaranteed Access Rule: Every piece of data must be accessible by a combination of the table name, primary key value, and column name. 
		--The Systematic Treatment of NULL Values: Null values must be handled in a systematic way to represent missing or inapplicable information. 
		--The Data Sublanguage Rule: All database operations must be supported through a single, linear language with a consistent syntax. 
		--The View Updating Rule: Any view that can be theoretically updated must also be updatable by the system. 
		--The High-Level Insert, Update, and Delete Rule: The system must support high-level operations like inserting, updating, and deleting not just single rows, but entire sets of data. 
		--Physical Data Independence: Changes to the physical storage structure should not affect applications that access the database. 
		--Logical Data Independence: Changes to the logical structure should not affect applications that do not use the modified part of the database. For example, splitting or merging tables should not impact user views. 
		--Integrity Independence: Constraints must be stored in the database's metadata and not in the application code, allowing them to be changed independently. 
		--Distribution Independence: Users should be unaware of how data is distributed across different locations; it should be transparent. 
--difference between logical and physical data model
	--logical data model defines the business rules and data structures in a platform-independent way using entities, attributes, and relationships, 
	--physical data model translates the logical model into a specific database implementation with tables, columns, data types, and other database-specific features. The logical model is created to understand business requirements, whereas the physical model is designed for efficient data storage and retrieval on a specific database platform. 
--index purpose - optional, independent schema object associated with a table or cluster, designed to accelerate data retrieval for SQL queries.
	--functions similarly to an index in a book, providing a quick lookup mechanism to locate specific data rows within a larger dataset.
	--Faster Data Access: Indexes create a sorted structure of one or more columns, allowing Oracle to quickly locate the physical address (ROWID) of the corresponding rows in the table without scanning the entire table.
	--Logical and Physical Independence: An index is separate from the table it references, meaning you can create, drop, or rebuild an index without affecting the data in the table.
	--Performance Optimization: Indexes are a crucial tool for performance tuning, significantly reducing the time required for queries, especially those with WHERE clauses, JOIN operations, or ORDER BY clauses on indexed columns.
	--Creation and Usage: Indexes are created using the CREATE INDEX statement and are automatically used by the Oracle optimizer when it determines that an index scan would be more efficient than a full table scan.
--Types of Indexes: Oracle supports various index types, including:
	--B-tree Indexes (default): The most common type, suitable for high-cardinality columns and range queries.

--ORA-01555 (Snapshot Too Old) -error occurs when a query requires data from the undo tablespace that has already been overwritten by other transactions
	--undo retention is the amount of time that committed undo data is kept in the undo tablespace. It ensures that long-running queries can access old versions of data for read consistency and supports Oracle Flashback features
		--Key Components of Undo Retention
			--UNDO_RETENTION Parameter: This initialization parameter specifies (in seconds) the minimum length of time the database attempts to retain undo data. The default value is typically 900 seconds (15 minutes).
			--Automatic Tuning: By default, Oracle automatically tunes the retention period based on current system activity and the size of the undo tablespace. It often retains undo longer than the specified UNDO_RETENTION if space allows.
			--Retention Guarantee: By default, Oracle may overwrite "unexpired" undo data (data younger than the retention period) if it needs space for new transactions. Enabling RETENTION GUARANTEE prevents this, though it may cause new transactions to fail if the undo tablespace fills up
	--Immediate Actions & Solutions
		--Increase Undo Retention: Increase the UNDO_RETENTION setting to a value higher than the duration of your longest-running query.
		--Resize Undo Tablespace: Ensure the undo tablespace is large enough to handle the retained data and set it to AUTOEXTEND ON. 
		--Optimize Queries: Tune the long-running query to read less data or run faster to reduce the risk of its required data being overwritten. 
		--Avoid Commits in Loops: Do not fetch data between commits in a cursor loop, as this frequently causes this error. 
			--placing a commit inside a loop that is inserting/updating/deleting can cause this error
		--Use RETENTION GUARANTEE: If necessary, configure the undo tablespace with the RETENTION GUARANTEE clause to force retention, even if it causes subsequent transactions to fail
--how to troubleshooting high CPU usage		
	--1. Identify the Culprit at the OS Level
		--First, confirm that the database is indeed the cause of high CPU. 
		--Linux/Unix: Use top or sar -u to identify high-CPU processes. Look for processes starting with oracle.
		--Windows: Use Process Explorer to see which threads within the oracle.exe process are spiking. 
	--2. Map OS Processes to Database Sessions
		--Once you have an Operating System Process ID (SPID), map it to an internal Oracle Session ID (SID) using the v$process and v$session views:
	--3. Analyze High-Impact SQL
		--If a few sessions are hogging resources, identify the exact SQL statement they are running: 
		--Active Sessions: Query v$sql using the sql_id found in the previous step.
		--Historical Analysis: Generate an AWR (Automatic Workload Repository) or ASH (Active Session History) report to see "SQL ordered by CPU Time". This highlights queries that may be efficient individually but run so frequently they drain the system	
	--4. Common Root Causes
		--Inefficient Execution Plans: Missing indexes or outdated statistics can force "Full Table Scans" instead of "Index Range Scans," drastically increasing logical I/O and CPU load.
		--Excessive Parsing: High "Hard Parse" rates (often due to not using bind variables) cause the CPU to work overtime just to compile SQL.
		--Parallelism Misconfiguration: Over-parallelizing queries can saturate all available CPU cores quickly.
		--Wait Events: High CPU can be a side effect of "spinning" for latches, such as latch: cache buffers chains or latch: shared pool. 
	--5. Quick Troubleshooting Tools
		--Oracle Enterprise Manager (OEM): Use the "Top Activity" or "Performance Hub" pages for a real-time visual of CPU-consuming sessions.
		--Autonomous Health Framework (AHF): Run tfactl diagcollect to gather automated diagnostic data for support or deep analysis
