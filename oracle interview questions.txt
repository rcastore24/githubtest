Q49. What do you understand by Redo Log file mirroring? =>safety feature that protects your database against data loss by maintaining identical copies of log files on different disks. 
--Key Concepts
	--Groups and Members: Redo logs are organized into groups. Mirroring is achieved by having multiple members within each group.
	--LGWR Writing: When a transaction occurs, the Log Writer (LGWR) process writes the change information to all members of the current redo log group concurrently.
	--Physical Separation: For effective mirroring, members of the same group should be placed on separate physical disks and controllers to eliminate a single point of failure.
--Why It Matters
	--Crash Recovery: Without mirrored logs, losing a single log file during a database failure can lead to catastrophic data loss, as you might only be able to recover up to the last available log entry.
	--Operational Continuity: If one member of a group becomes unavailable, Oracle continues to run by writing to the remaining healthy members.
	--Resilience over RAID: While hardware RAID provides protection, Oracle's internal multiplexing is often considered more resilient to software-induced corruptions.

q20 - how do you handle deadlocks in high-transaction systems
	--Key Strategies for Handling and Preventing Deadlocks
		--Implement Proper Indexing: The number one cause of deadlocks in Oracle is unindexed foreign keys. Ensure all foreign key columns are indexed to prevent excessive row-level or table-level locking.
		--Consistent Order of Operations: Ensure that all application modules update or lock tables in the same order (e.g., always lock TABLE_A before TABLE_B) to prevent circular waiting.
		--Keep Transactions Short: Long-running transactions hold locks longer, increasing the probability of contention. Design application logic to commit as soon as possible.
		--Use Exception Handling (ORA-00060): Program your application to catch the ORA-00060 error, roll back the transaction fully, and retry the operation after a short delay.
		--Avoid Intense Locking: Reduce the frequency of manual LOCK TABLE commands. Rely on Oracle's row-level locking mechanism.
		--Increase INITRANS: If contention is caused by many sessions updating the same block, increase INITRANS for tables and indexes to allow more Transaction List (ITL) slots in the block header.
			--physical storage parameter that defines the initial number of Interested Transaction List (ITL) slots allocated in the header of every data block for a table, cluster, or index.
			--controls how many concurrent transactions (INSERT, UPDATE, DELETE) can modify a specific block simultaneously without waiting
			-- It is useful for high-concurrency environments where many users update rows on the same block. Increasing it avoids contention but reduces the free space available for data in the block.
			-When to Increase INITRANS
				--High-concurrency systems (e.g., e-commerce, high-volume batch processing).
				--Tables or indexes with frequent, heavy concurrent updates.
